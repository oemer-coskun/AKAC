# ADR 017: supply chain and release integrity

Status: proposed for AKAC 0.6 (draft). No external review has taken place. Process
documents: [VERIFY-RELEASE.md](../docs/process/VERIFY-RELEASE.md),
[OPENSSF-BADGE.md](../docs/process/OPENSSF-BADGE.md). Workflows:
`.github/workflows/release.yml`, `ci.yml`, `scorecard.yml`.

## Context

Releases (tags `v*`) produced a signed container image only. A consumer had no signed source
archive, no SBOM attached to the release, and no check that the image build can be repeated.
OpenSSF Scorecard (run in CI) showed no signed-release evidence to look for because the release
carried no assets. Scorecard results read from the repository's code-scanning alerts on
2026-09-29: Pinned-Dependencies 9 (one unpinned base image in `bonus/openshell-profiles/lab`),
Security-Policy 4, Code-Review 0, Branch-Protection 4, CII-Best-Practices 0, Maintained 0 (repository
younger than 90 days). The public Scorecard API returned no result because `publish_results` was
false.

## Decision

1. **Release assets.** Each release carries: source tarball (`git archive` + `gzip -n`, so the
   bytes are a function of the commit), CycloneDX SBOM (`npm sbom`), a cosign keyless bundle
   (`*.sigstore.json`) for each of them, SLSA provenance `*.intoto.jsonl`, and `SHA256SUMS`.
   The container image is signed with cosign (keyless, OIDC), has a GitHub artifact attestation
   and BuildKit SBOM/provenance attached to the OCI index, and separate SLSA provenance.
2. **SLSA Build Level 3 claim, scoped.** Provenance is generated by the
   `slsa-framework/slsa-github-generator` reusable workflows (container and generic), which run
   the signing in an isolated workflow the build steps cannot influence; that is the documented
   basis for Build L3. The claim covers the release workflow's outputs only, is self-assessed and
   not third-party attested.
3. **Pinning exception.** All actions are pinned by full commit SHA. The generator workflows are
   referenced by tag `@v2.1.0` because that project documents that it MUST be referenced by tag
   `vX.Y.Z` (a SHA or a short tag makes the generator fail, as `slsa-verifier` needs the ref to
   resolve the builder identity). The tag was resolved to commit
   `f7dd8c54c2067bafc12ca7a55595d5ee9b75204a` when written. Mitigations: Dependabot watches the
   reference, the reusable workflow is the sole tag-pinned reference, and the tag is on a repository
   of an organisation under the OpenSSF. Scorecard's Pinned-Dependencies check may still report
   it; that is accepted.
4. **Maintenance risk of the generator.** Its README states it is no longer actively maintained
   and recommends GitHub artifact attestations, which are verified with `gh attestation verify`
   rather than `slsa-verifier`. Both are produced here so consumers can use either and the
   project can drop the generator if it stops working (for example after a Node runtime
   deprecation) without losing signed provenance. Revisit at every minor release.
5. **Reproducible image build check.** CI builds the image twice from two independent checkouts
   (different path and file times, `--no-cache`) with `SOURCE_DATE_EPOCH` set to the commit time
   and BuildKit `rewrite-timestamp=true`, single platform `linux/amd64`, attestations off, and
   compares the OCI manifest digest. The release build uses the same flags. Not covered: the
   multi-arch index digest (it contains attestation manifests that carry run-specific data), the
   `arm64` build (emulated, not compared), and byte-identity between different BuildKit versions.
   A local run on one host produced identical digests; that is a single observation, not proof.
6. **Least privilege.** Workflow-level `permissions: contents: read`; write scopes only on the
   job that needs them (`packages`, `id-token`, `attestations`, `contents: write` for the release
   job). Checkouts use `persist-credentials: false`.
7. **Scorecard.** `publish_results: true` so the public score and badge exist. Fixable now:
   Security-Policy (links and process in SECURITY.md), Signed-Releases (assets above), Pinned
   (SHA pinning; the lab base image is outside this change), Dependency-Update-Tool (Dependabot),
   SAST (CodeQL), Fuzzing (Scorecard detects property-based tests by an import of `fast-check`,
   verified in its source; the test suite already imports it). Owner-side: Branch-Protection,
   Code-Review (needs a second reviewer), CII badge.
8. **Runtime footprint.** Dependencies stay `jose` and `pg` only; every addition needs an ADR
   line stating why it exists.

## Consequences

Consumers can verify a release with three independent mechanisms. A release takes longer (extra
jobs). If the reproducibility check fails on a routine change it is a defect to fix, not to
disable. A compromised maintainer account or a compromised GitHub Actions platform is not
addressed by any of this.
